# Gen2.4.2 SPIN05 diagnostic image

Baseline repository commit: `182919ead170b160e82eaa428ae9c08076547af2`.
The pre-existing local change before this diagnostic work removes `noinline` from `cfgFlag()` in `Src/hardware.c` so GCC 14.2 can link the full main image; `configs/gen2_4_2_ghost.{json,md}` contain the Ghost pin mapping. This diagnostic adds `Diagnostics/main.c`, `Diagnostics/startup.c`, and the independent `diagnostic` Make target. `tools/mm32flash.py` was changed only to pass `auto_unlock=False` explicitly to pyOCD. `git diff` and `git status --short` show the complete working-tree changes; the main firmware sources and power-bridge logic are not used by this image.

Build from the repository root:

```sh
make MCU=SPIN05 CROSS=/home/zyoung/.local/opt/arm-gnu-toolchain-14.2.rel1-x86_64-arm-none-eabi/bin/arm-none-eabi- diagnostic
```

Outputs: `HoverBoardMindMotion/build/spin05/diagnostic.{elf,bin,hex}`. Flash load is 1,688 bytes, ending at `0x08000698`, well before the config page at `0x08007C00`; RAM use is 1,048 bytes. The image has its own startup and links only the vendor `SystemInit()` and diagnostic source. It does not reference TIM1, the motor-control sources, or PWM alternate functions. The six bridge-control GPIOs are explicitly configured as floating inputs. The driver input bias with floating MCU pins has not yet been measured, so this image is **not cleared for a powered bridge**.

At boot the image sets PB2 high (power hold) without waiting for PB5 button release. It then sends `GEN2.4.2 DIAG SPIN05 115200 8N1` and a line every 500 ms on UART1 PB6 TX (open drain), with PB4 RX. Each line reports milliseconds, raw Hall bits (PC15/PC14/PC13), PB5 input, PB2 output, PB1 ADC channel 9 raw count, and an ADC valid flag. The status is also available by SWD at the `diagnostic_status` symbol (`0x20000008` in the present ELF). No battery-voltage conversion is attempted because the divider ratio is unknown. A UART receiver needs a suitable pull-up and must be voltage compatible with the board.

The existing `tools/mm32flash.py` uses pyOCD's CMSIS-DAP transport with a generic `cortex_m` target and writes the MM32 Flash registers directly. For a 1,688-byte BIN it would erase `0x08000000` through `0x08007BFF` in 1 KB pages, leave the last 1 KB config page untouched, program halfwords through a RAM routine, read back all 1,688 bytes and compare them, then start the image. `--start reset` would be needed here: its default soft start preserves AHB GPIO state from the old firmware, which could leave PWM pins in alternate-function mode until the diagnostic changes them. With SW held, a system reset should keep board power on.

**No erase or program has been executed.** Preflight found CPUID `0x410CC200`, DBGMCU IDCODE `0xCC4460B1`, FLASH CR `0x80` (locked), SR `0`, WRPR `0xFFFFFFFF`, OBR `0x03FFFC1E`, and SWD reads of both code and config Flash returning zero. A later read of the 16 option-byte addresses at `0x1FFFF800` also returned all zero (`build/spin05/diagnostic-option-read.log`). The manufacturer's MM32SPIN05x manual marks OBR bit 1 as reserved, so these reads do not establish the read-protection state or the correct recovery procedure. The installed CMSIS-Pack target `mm32spin05pf` reports 32 KB Flash, 1 KB sectors and 4 KB RAM; it has no separate PFOP target. The measured SWDIO static high is 3.3 V; the manufacturer's data sheet specifies an input high threshold of at least 0.7 × VDD, which would be 3.5 V if MCU VDD is 5.0 V. Eight read-only reconnects succeeded at 100 kHz, but that does not certify the voltage margin. The supply currently displays zero current; MCU VDD and CV/CC state have not been reported. These are the remaining flash gates, together with the unverified HIN/LIN bias of the floating bridge inputs.
