# Gen2.4.2 formal firmware burn, 2026-11-03

Baseline repository commit: `182919ead170b160e82eaa428ae9c08076547af2`.
Target: one user-connected MM32SPIN05PFOP, DAPLink UID `F45C7948E30E29288708BD68764F9178`, generic `cortex_m` SWD target at 10 kHz with `auto_unlock=false`.

The Ghost profile is `configs/gen2_4_2_ghost.json`. Main firmware was rebuilt with a minimal boot-disarm fix: `wState` includes `STATE_DISABLE`, `axisState=AXIS_IDLE`, `gatesoff=1`, TIM1 BDTR initialization omits AOE. `gatesOutput()` was expressed as one read/modify/write to fit the 31 KB code area. No PWM pins, polarity, dead time, or commutation logic were changed. The compiled ELF uses 31 KB Flash exactly and 2,760 B RAM including the reserved stack. Firmware BIN length is 31,744 B; config starts at `0x08007C00`.

The first combined image was generated from the existing JSON using the author's `image.js` layout (extension slot 0, main slot 1) and parsed with `mm32cfgstore.py`. It was 32,000 B. Burn command:

```sh
.venv/bin/python tools/mm32flash.py HoverBoardMindMotion/build/spin05/hoverboard-ghost-gen2_4_2-id1.bin --frequency 10000 --probe F45C7948E30E29288708BD68764F9178 --start none
```

Log: `HoverBoardMindMotion/build/spin05/ghost-formal-flash.log`. The tool reported `programmed and verified 32000 bytes, erased 0x08000000-0x08008000 (config from the image)` and left the core halted. An independent generic-target readback of all 32 KB matched the first image for all 32,000 bytes, SHA-256 `e3aa76d8d7364ea2e953855cd26ec2be70bf1403fe8436e83ed3675dd8db31cb`; the remaining 768 B were `0xFF`. Log: `ghost-formal-independent-verify.log`.

A soft start ran the new image. At about 2 seconds: core RUNNING; TIM1 BDTR `0x3C24` (MOE and AOE both clear); `gatesoff=1`, `axisState=1` (IDLE), `wState=96` (battery LED + disable), `realspeed=0`; GPIOB ODR at its actual offset `0x4800040C` was `0x44` (PB2 high). Logs: `ghost-formal-softstart.log`, `ghost-formal-live-read.log`. UART CANSimple requests on `/dev/ttyACM0` returned no responses (`ghost-formal-uart-query.log`). The firmware uses open-drain UART TX by default; DAPLink VCOM may lack the pull-up. The first image configured `vbatdivider=47` from an incorrect calculation. Firmware reported ~56.2 V while the user reported a 36 V supply, and `axisErrors=0x100` (overvoltage). The source-derived scale correction is approximately `47*36/56.2 = 30`; this is still provisional until confirmed by telemetry.

The JSON was updated to `vbatdivider=30` and `txpushpull=2` (single-board UART push-pull). The new image was rebuilt with the author's `image.js`, 32,000 B, SHA-256 `94653eb9ec2df49261d787687e7e8c3a4c8856dc556b4f05031dd7b6f37c3219`, and parsed by the repository's `mm32cfgstore.parse_new()`.

**Second burn attempt did not erase or program.** `mm32flash.py` failed in `Mm32.halt()` while reading core register `r12`, before reaching `mcu.erase()`; log `ghost-formal-flash-v2.log`. The following read-only SWD attach failed with `No ACK` at DP discovery; log `ghost-formal-after-failed-reflash-readonly.log`. No further write or unlock was attempted. The target likely lost self-hold after the halt error and watchdog reset, but this is an inference until the user's 5 V check. The target's flash is expected to contain the first verified formal image (divider 47, open-drain UART); this could not be reconfirmed after the No-ACK event. The local JSON and combined BIN are now **newer than the target image**. No motor command was sent.

## Corrected image written after reconnection

The user reported the SW wiring had not been seated correctly and restored the 36 V supply. A full read-only 32,000 B flash read at 10 kHz verified that the first image was intact (`ghost-formal-fixed-connection-preflight.log`). Two later `mm32flash.py` attempts failed at the same core register `r12` before erase. The cause was the script's `Mm32.halt()` order: at 10 kHz it halted a running watchdog-enabled firmware and tried to read all registers and RAM before setting DBGMCU IWDG_STOP; the ~500 ms watchdog reset the target. The script was changed to enable the debug clock and IWDG_STOP before the halt. A no-Flash-write halt/resume test saved all 21 core registers and 1,024 RAM words and restored RUNNING state (`ghost-formal-watchdog-halt-test.log`).

The corrected 32,000 B image was then written with the same `mm32flash.py` command at 10 kHz, `--start none`; the tool reported programming and internal verification success (`ghost-formal-flash-v2-watchdog-fixed.log`). A separate read-only SWD session read all 32 KB. The image SHA-256 and readback SHA-256 were both `94653eb9ec2df49261d787687e7e8c3a4c8856dc556b4f05031dd7b6f37c3219`, mismatch count 0; the remaining 768 B were `0xFF` (`ghost-formal-v2-independent-verify.log`).

After `Mm32.soft_start()`, core RUNNING, TIM1 BDTR `0x3C24` (MOE/AOE clear), `gatesoff=1`, `axisState=1` (IDLE), `wState=96` (disabled), PB2 ODR high, `realspeed=0`, `axisErrors=0`, `vbat=3569` (~35.69 V at reported 36 V supply). Log: `ghost-formal-v2-start.log`. The corrected voltage scale is plausible but is only a single-point calibration.

CANSimple `get_version`, heartbeat, encoder, bus voltage/current, and Iq requests returned no frames (`ghost-formal-v2-uart-query.log`). A safe CANSimple IDLE frame `a501070401000000928f` was sent three times (`ghost-formal-v2-idle-send.log`); SWD then read `cmdSource=1`, so the MCU had not parsed it. PB4 RX input was low at idle (`GPIOB_IDR=0x6C`), despite the configured PB4 AF3 and PB6 AF0. `gatesoff=1` and MOE/AOE remained clear (`ghost-formal-v2-idle-recv-check.log`). This points to a missing/miswired or incompatible host VCOM TX to PB4 connection; the user was asked to verify its idle level is ~3.3 V before connecting. No nonzero setpoint, ARM, PWM output, or motor calibration command was sent.

The user confirmed that only board PB6 TX -> DAPLink VCOM RX had been connected; DAPLink VCOM TX -> PB4 was absent. This explains the no-response and PB4 idle-low observations without implicating firmware UART code. The user measured the bus at 36.02 V, versus firmware telemetry 35.69 V (about -0.9 %), so the provisional divider 30 is reasonable at this operating point. The DAPLink VCOM TX idle voltage still needs checking against the 3.3 V MCU input before wiring it to PB4.

## 2026-11-22: R004 shunt and first-run protection image prepared

The user powered the board off and read the bus shunt marking as **R004** (4 mΩ). Ghost's annotated photo labels PA7 as the direct bus current sense. The author's `pinout.h` and `pf_detect.c` define `itotaldivider` as the reciprocal of the shunt resistance in ohms, so the local profile now uses `itotaldivider=250`. The idle VREF ADC count 948 implies about 1.27 mV/ADC count, or 0.32 A/count for a direct 4 mΩ shunt. This is a source-derived estimate, not a loaded current calibration.

For a conservative bench trial, the local profile also now sets `softocp=2` A (averaged bus-current limit) and `hardocp=8` ADC counts above the learned zero (about 2.5 A on the direct shunt). These values are provisional. The firmware's ADC watchdog generates a TIM1 break and holds outputs off for two control periods, but the hardware trip behavior has not been exercised. The target still has the earlier effective configuration with all three values unset; this updated image has **not** been flashed and no UART save has been sent.

The official web console image builder regenerated `HoverBoardMindMotion/build/spin05/hoverboard-ghost-gen2_4_2-id1.bin` from the JSON and the existing main firmware BIN. It is 32,000 bytes, SHA-256 `4d94f14faa4be735ffe3f8a3e66a9f91ccc4fec662db2bc5da99e31a52e2055a`; firmware bytes 0..31743 match the already flashed main firmware exactly, the config begins at `0x08007C00`, and `mm32cfgstore.parse_new()` reads `itotaldivider=250`, `softocp=2`, `hardocp=8`, `windings=16`, `batfull=42000`, `drivemode=1`, `slaveid=1`.

The U3116S vendor datasheet identifies HIN and LIN as in-phase (active-high) inputs, versus U3115S's inverted LIN. This alone does not establish whether the Ghost PCB has an inversion stage between PB13 and the A-phase U3116S LIN pin. A single powered-off resistance/trace check is needed before the first ARM. The existing firmware default `invlowside` is normal (unset), with 500 ns TIM1 dead time; neither was changed.

The user measured **1 kΩ from MCU PB13 (LQFP48 pin 26) to the A-phase U3116S LIN (pin 3)** with the board unpowered and the bus capacitors discharged. This is consistent with a direct series resistor between TIM1_CH1N and the driver logic input, without an intervening inverting transistor on that phase. Combined with the U3116S active-high LIN input, it supports the firmware's existing normal low-side polarity. It is one measured path; the B/C paths are inferred from the repeated Ghost layout and have not been individually measured. No low-side polarity or dead-time setting was changed. The protection image is still local; power is off awaiting a safe IDLE read before UART configuration writes.
