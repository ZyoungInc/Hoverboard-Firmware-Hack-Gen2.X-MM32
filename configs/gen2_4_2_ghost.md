# Gen2.4.2 (old 2.8.1), MM32SPIN05PFOP

Source: Ghost's [annotated PCB image](https://github.com/RoboDurden/Hoverboard-Firmware-Hack-Gen2.x/issues/59#issuecomment-1921944539), the SPIN05 pin tables in `HoverBoardMindMotion/Src/hardware.c`, and the current configuration schema in `tools/cfgfields.py`.

`gen2_4_2_ghost.json` uses the existing `hoverboard-pinfinder-config` export format accepted by the author's web `image.html`. It specifies only PCB signals confirmed by the image and source. PWM pins are fixed by TIM1 hardware and `BLDC_init()`, not config words: A_H/PA8, A_L/PB13, B_H/PA9, B_L/PB14, C_H/PA10, C_L/PB15. Ghost's physical Hall pads are PC15/PC14/PC13; the motor-specific electrical assignment was calibrated as `halla=PC14`, `hallb=PC13`, `hallc=PC15`, `hallinvert=1` on 2026-11-22. The master/slave connector's UART TX/RX are PB6/PB4 (UART1). The RGB connector exposes PD3/PD2/PA12, and the separate LED is PA15; color order and LED role have not been established, so the profile does not assign them. I2C is on PD1/PD0, but the sensor type is unknown and the profile leaves IMU disabled.

**This is a commissioning configuration, not yet approved for motor output.** It maps the known PA2 and PA6 PFOP internal amplifier outputs to the existing FOC ADC channels, but leaves `iphasecfg`, `iphasegain`, `ocp`, and `ocpref` unset. Ghost marks PA1/PA2 and PA5/PA6 paths, but the photo does not prove which output measures which motor phase or the current sign. PB0 is marked Estop in the photo, but is not a TIM1 BKIN alternate-function pin in `hardware.c`, so it is not assigned to `ocp`. PA3's comparator-reference role is uncertain. The user read R004 on the bus shunt; the prepared profile uses `itotaldivider=250`, `softocp=2` A, and `hardocp=8` ADC counts as provisional first-run settings. LED polarities and any MCU-to-U3116S input inversion remain unverified. The profile selects block speed mode (`drivemode=1`) and node ID 1; FOC needs further calibration.

The U3116S [truth table](https://datasheet.lcsc.com/lcsc/2003312026_UNI-SEMI-U3116S_C400131.pdf) specifies active-high HIN/LIN. It does not establish the complete PCB signal path from the MCU to those inputs. The firmware defaults to a 500 ns TIM1 dead time (`initialize.c`), and `invlowside` defaults to non-inverted; neither value is validated for this board. The local boot-disarm patch removes AOE from `TIM1_init()` and boots with `gatesoff=1`, CANSimple IDLE and v1 disabled. SWD confirmed MOE/AOE were clear after first boot. PWM output must remain unarmed until the gate signal path and protection are checked.

The current firmware stores board configuration in the final 1 KB flash page at `0x08007C00`, with an extension record followed by a main record. The JSON omits unknown calibration values; the web image builder fills omitted words with `0xFFFF`. `vbatdivider=30` is an empirical estimate from the first formal boot's reported ~56.2 V at the user's measured 36 V supply with divider 47. It must be confirmed through telemetry. `txpushpull=2` is for the one board connected to DAPLink VCOM; use open drain and a pull-up when multiple boards share the bus. Main firmware has no motor auto-calibration commands. PinFinder's `calibrate poles` asks for one manual wheel revolution with gates off; `calibrate hall`, `calibrate rl`, and `calibrate kv` drive the bridge.

`main.c` waits for button release after setting PB2 high. The user had released SW before first formal boot, and SWD confirmed PB2 output remained high. The first formal image was flashed and independently verified, then started with TIM1 MOE/AOE clear. See `FORMAL_BURN_2026-11-03.md` for logs and the failed second flash attempt.

Diagnostic results on 2026-11-03: the user's MCU VDD measurement at its decoupling capacitor was 3.3 V; a separate board pad is 5 V. The minimal no-TIM1 diagnostic image was flashed and all 1,688 bytes were read back with zero mismatches. It runs and streams UART1 on PB6 at 115200 8N1. With SW released, the board's 5 V rail and UART output remained present while PB2 output stayed high. The user confirmed PB5 is the button input and asked to skip further PB5 measurement; its raw value was 0 both before and after SW release, so button polarity/transition remains unverified. No motor or Hall harness is connected, so Hall raw value 7 is an open-connector observation, not a Hall test. The PB1 ADC reported a stable raw count near 945 at 36 V bus, without a calibrated voltage divider. None of these results validates bridge PWM polarity, dead time, current phase mapping, or overcurrent protection.

2026-11-22 update: the motor phase and Hall harness are connected; UART, PB2 hold, battery voltage, Hall transitions and eight pole pairs were verified while the axis stayed IDLE. `windings=16` and `batfull=42000` are saved on the chip. The user measured 1 kΩ between MCU PB13 and the A-phase U3116S LIN input with power off, supporting a direct normal-polarity low-side path; the other two repeated paths were not individually measured. The R004 protection values (`itotaldivider=250`, `softocp=2`, `hardocp=8`) were saved via CANSimple, read back independently from Flash, and applied by a SWD soft start. ADCMPR read `0x00080000`; the ADC watchdog has not yet been exercised by actual current. The local combined image carries the same effective configuration but was not re-flashed because the live SDO save succeeded. See `FORMAL_BURN_2026-11-03.md` for live readback and the image hash.

Later on 2026-11-22, the fixed-pin Hall calibration succeeded at 1500 mV, giving the motor-specific assignment above with `lead90=5`. The new board-specific main build `make MCU=SPIN05 BOARD=GHOST_GEN242` omits IMU initialization and polling because this profile has no configured IMU; it retains FOC, CANSimple and current protection. It uses 29,436 B of the 31 KB code area and 2,612 B RAM. The combined image was flashed and independently verified, and the main firmware starts IDLE with the bridge off. See `HALLMAP_2026-11-22.md` for the calibration and flash logs.

The subsequent user-run low-speed test moved the wheel slowly in one direction and stopped quickly; one negative instantaneous velocity sample while cumulative position increased caused the host script to abort. The user reports rust-related drag. The 42.01 V supply reference was used to set and persist `vbatgain=30370` (on-chip config slot 3), giving 42.005 V mean telemetry. The local JSON and prepared combined image now include this gain, though the newly generated image was not re-flashed because the live save was verified.

The later user-run 7% block-voltage pulse proved forward commutation but accelerated the unloaded wheel to about 3 turns/s within 0.21 s; the host stopped on its travel/speed bound, and the user observed only about 1 W on the bench supply. The board returned to IDLE, 0 A and `drivemode=1` with no error. The open-loop pulse is not extended. A 3 s, 0.25 turn/s closed-loop speed test with a temporary firmware overspeed guard is prepared and its non-driving check and stop paths passed; it has not been run yet.
